# Jog Confirmation Research: What Can Confirm an M5C Move?

**This is an input to a design discussion, not a ledger entry.** Nothing here was
tested against the printer during this investigation; every command reference is
read from source, from captured evidence already recorded, or from a published
first-party repository. Fold what survives review into
[`printer-findings.md`](printer-findings.md) deliberately.

> **Update, 2026-07-27 — open question 1 is closed.** A read-only
> `scripts/printer-probe.py status` run enumerated the burst after this document
> was written: **it carries no position field**, `CONFIRMED`. The full thirteen
> non-temperature types are in the ledger's 2026-07-27 entry. This *strengthens*
> the recommendation below (option A) rather than changing it — `M114` is now the
> confirmed-only position path, not the presumed-only one. The run did **not**
> settle the contested `1005` row: it read `1005: 0` with the fan off, which fits
> either reading. The analysis below is left as written, at its original grades.

**The question.** Issue #12 (bounded jog) is unblocked but unimplementable:
`FACT_PATHS` in `web/printer_snapshot.py:14-30` contains no position fact, so a
jog action has nothing to confirm against. Before designing a confirmation
contract we need to know what the protocol actually offers.

## Three things that must not be conflated

This document keeps them in separate columns throughout, because collapsing them
is the specific failure mode that produced the current jog implementation.

| | Meaning |
| --- | --- |
| **Declared** | A name exists in a generated protocol table. Says nothing about behavior. |
| **Observed (app)** | Someone watched the official eufyMake app put this on the wire. |
| **This codebase** | What `ankerctl` actually sends today. |

Status grades follow `printer-findings.md`: `CONFIRMED` (directly observed,
reproduced, or read from firmware source), `STRONG`/`LIKELY`, `UNVERIFIED`
(plausible, untested — do not act as if true), `REFUTED`.

## 1. `MOVE_STEP` (0x400) and `MOVE_DIRECTION` (0x401)

### What the protocol declares

Both opcodes are declared in three places in this repo, and **all three are the
same generated artifact** — `libflagship/mqtt.py` carries a "GENERATED BY
TRANSWARP / DO NOT EDIT" banner at its head, and `static/libflagship.js` and
`specification/mqtt.stf` are its siblings:

- `libflagship/mqtt.py:44-45` — `ZZ_MQTT_CMD_MOVE_STEP = 0x0400 #` and
  `ZZ_MQTT_CMD_MOVE_DIRECTION = 0x0401 #`. **The trailing comments are empty.**
- `specification/mqtt.stf:109-113` — the source of that generation. Each opcode's
  documentation block is a bare `#`.
- `static/libflagship.js:25-26` — same values, no annotation.

Compare the neighbors: `MOVE_ZERO` (0x402) carries "(probably) Move to home
position"; `EXTRUSION_STEP` (0x3fe) carries "(probably) run the extrusion
stepper"; `GCODE_COMMAND` (0x413) carries a full field list. The two jog-shaped
opcodes are the ones with **nothing written next to them at all.**

`CONFIRMED`: the declaration is a name and a number. No payload, no field list,
no semantics.

**The upstream project has no more than we do.** The most complete public
reverse-engineering of this protocol,
[`Ankermgmt/ankermake-m5-research/mqtt/message-types.md`](https://github.com/Ankermgmt/ankermake-m5-research/blob/master/mqtt/message-types.md),
enumerates every message type with a Description and a Fields column. Rows 1024
and 1025 (`MOVE_STEP`, `MOVE_DIRECTION`) have **both columns blank** — while
1023 above them lists `flag=?, stepLen=?, temperature=?` and 1026 below them
lists `value=?`. Someone got far enough to guess fields for the neighbors and
recorded nothing for these two. `CONFIRMED`.

A GitHub-wide code search for `ZZ_MQTT_CMD_MOVE_DIRECTION` returns 10 files
across 5 repositories; every one is a copy of the same generated table
(`Ankermgmt/ankermake-m5-protocol`, `treitmayr/…_from-anselor`,
`GRA5S/ankermake-home-assistant`, `Django1982/ankerctl_go_remake`, and the
research doc above). **Not one implementation exists anywhere public.**
`CONFIRMED`.

### What the original app was observed to send

**Nothing. There is no observation.** `UNVERIFIED`.

This is the single most important correction in this document. The project
memory note `m5c-jog-uses-dedicated-opcodes` asserts "The original AnkerMake app
jogs with dedicated MQTT opcodes" and treats that as established. Its own body
then concedes the opcodes have "no payload definitions, no captures, and no
entries in `documentation/printer-findings.md`." The belief rests entirely on the
names `MOVE_STEP` and `MOVE_DIRECTION` sounding like jog.

The names are decent circumstantial evidence — `MOVE_ZERO` (0x402) sits right
after them and *was* confirmed to be the app's Home operation
(`local-macos-service.md:314-316`: eufyMake's app-level `MOVE_ZERO`,
`commandType: 1026, value: 2`, drove the nozzle into the plate on a supervised
test). A contiguous `MOVE_STEP` / `MOVE_DIRECTION` / `MOVE_ZERO` triple reads
naturally as *distance*, *axis+sign*, *home*. That is a reasonable hypothesis and
it should be written down as one.

It is **not** a finding, and it must not become the justification for building
issue #12 on those opcodes. Grade: `UNVERIFIED`, with the name-adjacency argument
worth `LIKELY` at most and no more.

### Where the wire format could be read — and where it cannot

The memory note's actionable claim is that the format "is readable in the
published M5C firmware source." **That is false.** `REFUTED`:

- `github.com/eufymake/eufyMake-Marlin-M5C` is the **Marlin MCU firmware only**.
  A code search of that repository for `ZZ_MQTT` returns **0 results**; for
  `real_print_layer` (a field seen in the 1052 notice), **0 results**. The single
  hit for `commandType` is in `HAL/STM32/tft/tft_ltdc.cpp` and is unrelated.
- That is architecturally expected and already recorded here:
  `local-control-research.md:229-231` concludes "The M5C's Linux 'upper computer'
  bridges Anker MQTT to the Marlin MCU and owns job execution." The MQTT opcode
  table is parsed by that Linux module. ~~**It has never been published.**~~
  **Corrected 2026-07-27: that claim was wrong and was reached by searching only
  the Marlin repo.** `eufymake/eufyMake-linux-sdk` is published (GPL-3.0). Its
  top level is BSP-shaped — `bootloader`, `buildroot`, `kernel`,
  `module_driver` — so it may not carry the MQTT application, but that has to be
  checked rather than assumed. Two more vendor trees in the Marlin repo were
  also missed and are directly relevant: `src/gcode/anker_gcode/` and
  `src/feature/anker/` (fourteen modules, including `anker_homing`,
  `anker_z_sensorless`, `anker_z_offset`, `anker_pause`, and `handshake`).

Consequently the only ways to learn the payload shape of 0x400/0x401 are:

1. **Capture the official eufyMake app jogging the printer** through the local
   broker and read what it publishes. This is the decisive experiment, it is
   read-only from our side (we observe; the app commands), and the local-broker
   stack already positions us to see every publish. It does require the operator
   to be present, because the *app* will move the printer.
2. Extract and reverse the Linux module from a firmware image. Large, and
   nothing in this project has needed it yet.
3. Reverse the mobile app binary. Third-party, out of scope here.

Option 1 is cheap and would settle questions 1 and 2 of this document at once.

### Does either opcode produce a reply, and does any reply carry position?

**No evidence either way.** `UNVERIFIED`. Neither opcode has ever been sent by
this project (see below), so no reply has ever been seen.

What can be said about the general shape: `ctrl_send_mqtt` in `web/__init__.py:298-355`
correlates replies by matching `commandType`, and `web/printer_actions.py:840-849`
shows the same pattern for `1008` — so the printer's Linux module does answer
non-G-code opcodes on their own command type. Whether a `0x400`/`0x401` reply
exists, and whether it would carry a coordinate, is entirely unknown.

### What this codebase does

**It never sends either opcode.** `CONFIRMED`.

- `git log --all -S"MOVE_STEP"` returns exactly three commits — `87cb928` (added
  the `.stf` specification), `c509859` (snapshot the generated `mqtt.py`), and
  `8c0354d` (snapshot the generated `libflagship.js`). **Every occurrence in
  history is the declaration arriving; none is a use.** There is no abandoned
  implementation, no reverted branch, no capture.
- The actual jog is raw G-code, invented here: `static/ankersrv.js:1175-1187`
  sends `G91`, then `G1 <axis><step> F<feed>`, then `G90` as three separate MQTT
  messages (feed 600 for Z, 3000 for X/Y).
- `tests/test_browser_ui.py:936-941` pins that exact sequence as the expected
  wire output.
- `tests/test_live_printer.py:150-167` is the live fixture, gated on
  `ANKERCTL_TEST_ALLOW_MOTION`. **It asserts nothing about position** — it sends
  the three lines per axis and checks only that each was accepted.

The consequence is already `CONFIRMED` in the ledger: raw relative X/Y moves are
refused by Marlin's unhomed-axis guard, every reply carrying `echo:Home X` /
`echo:Home Y`, across 1mm, 10mm, and 3×50mm supervised sequences
(`printer-findings.md:307-310`). Z jog works because Marlin permits unhomed
relative Z.

## 2. Position in telemetry

### The pushed stream carries no position

`CONFIRMED`, now with a firmware-source root cause rather than only an
observational one.

The V8110_DVT build has Marlin's position auto-report **compiled out**, while
temperature auto-report is compiled in
([`Configuration_adv.h`](https://github.com/eufymake/eufyMake-Marlin-M5C/blob/main/release_marlin2.0/Marlin/Configuration/V8110/V8110_DVT/Configuration_adv.h)):

```
3644:#define AUTO_REPORT_TEMPERATURES
3649://#define AUTO_REPORT_POSITION
```

`M154 S<seconds>` — the G-code that would make the MCU stream position on a timer
— **does not exist in this build**. That is the mechanical reason the ledger's
"The M5C never publishes `state`. It pushes temperatures only."
(`printer-findings.md:534`) extends to position: the firmware was configured to
push exactly one thing, and it is temperature.

Three independent lines of corroboration:

1. **This codebase.** `web/service/state.py:30-71` normalizes command types 1000
   (subType 1 → state), 1001, 1003, 1004, 1006, and 1052. No position path
   exists. `web/service/mqtt.py:26-32` routes every decoded object through that
   normalizer into `printer_snapshots.observe()` — so **whatever the normalizer
   does not name can never become a fact**, no matter what the printer sends.
2. **An independent mature consumer.** The Home Assistant integration
   [`sondregronas/ankermake-hass-component`](https://github.com/sondregronas/ankermake-hass-component)
   consumes the same live MQTT stream. Its `AnkerData` model
   (`custom_components/ankermake/anker_models.py`) has fields for temperatures,
   progress, layers, speed, fan, nozzle type, leveling, filament, and errors —
   **no coordinate field of any kind** — and its adapter handles 1001, 1003,
   1004, 1005, 1006, 1008, 1037, 1052, 1055, 1068, 1072, 1085, 1093.
3. **The upstream research table.** No row in
   `Ankermgmt/ankermake-m5-research/mqtt/message-types.md` describes a position
   field.

### The `APP_QUERY_STATUS` (1027) burst — enumeration attempted, and it fails honestly

**The full enumeration does not exist and was never recorded.** `CONFIRMED` as a
gap.

`printer-findings.md:45` says the burst returns "~16 telemetry types" and names
five. I checked whether a fuller list survives anywhere: `git log -S"1098"` and
`-S"1067"` each return a single commit (`0d80e46`, the one that wrote that very
row), the 205MB `ankerctl.log` contains **zero** occurrences of `commandType`
(it is a Flask access log), and no capture file, pcap, or fixture in the
repository embeds a real notice payload — `tests/fixtures/` holds only five
G-code files, and `tests/test_decode_pppp_pcap.py` synthesizes its own frames.

Assembling every type ever named across the two surviving records — the ledger
and the `m5c-telemetry-poll-gap` memory note (2026-07-09 burst, cloud MQTT) —
gives this partial reconstruction. **It is a floor, not the enumeration.**

That is 13 named against "~16". **Around three to six types have never been
decoded, and 1067/1097/1098 are only partially decoded.** Therefore:

> **Whether the 1027 burst contains position is `UNVERIFIED`, and the honest
> answer is "we do not know."** No recorded evidence shows position in it. No
> recorded evidence rules it out either, because the burst was never fully
> transcribed.

This gap is **cheap to close and read-only**: `scripts/printer-probe.py status`
(`scripts/printer-probe.py:135-153`) already sends `{"commandType": 1027}` and
prints every non-temperature reply it collects, keyed by command type. One run
with the output pasted into the ledger would settle it. `printer-findings.md:95`
already flags that this subcommand's live path is itself `UNVERIFIED` and should
be tested before it is trusted — which makes the run doubly worth doing.

Note this is a *weak* prior for finding position there: a 1027 status burst is
job/config-shaped (leveling, filament, buttons, breakpoint), and the firmware
side has no position push to bridge. But "unlikely" is not "checked."

### One contested row worth flagging, not resolving here

The `m5c-telemetry-poll-gap` memory note records **1005 fan speed** as part of
the 2026-07-09 burst, and the Home Assistant adapter treats 1005 as an inbound
`fan_speed` value. The ledger states at `CONFIRMED` grade that "the status and
`M105` replies expose no fan-state field" (`printer-findings.md:354`), which is
the basis for `fan_setting` being permanently unconfirmable
(`handoff.md`, "The `fan_setting` decision").

I did not re-derive this and I am not proposing to reopen it — the ledger wins.
Two facts belong in the operator's hands anyway:

- The HASS component targets the **M5**, not the M5C. A type present on one and
  absent on the other is entirely ordinary for this protocol family.
- The firmware confirms the *serial-side* fan silence independently:
  `Configuration_adv.h:3708` has `//#define REPORT_FAN_CHANGE` commented out, so
  the MCU never echoes a fan speed. That explains `M105`'s silence, and it is
  new corroboration for the ledger's conclusion rather than against it.

If the 1027 enumeration run above is ever done, it answers this for free.

### Is position in the same situation as `fan_setting`?

**No, and the difference is the whole reason issue #12 is not hopeless.**
`CONFIRMED`.

| | `fan_setting` | position |
| --- | --- | --- |
| Pushed by the printer? | No | No |
| Available on request? | **No — no query returns it** | **Yes — `M114`, proven** |
| Firmware reason | `//#define REPORT_FAN_CHANGE` | `//#define AUTO_REPORT_POSITION` |
| Can an action confirm? | Never, by protocol | Yes, if something asks |

`fan_setting` resolves `indeterminate/confirmation_unavailable` because the fact
does not exist anywhere at any price. Position exists, is precise, and is one
round trip away. The blocker for jog is **architectural, not protocol-level**:
the snapshot only ingests what `normalize()` names, and nothing polls `M114`.

## 3. `M114`

### The round trip is confirmed, repeatedly

`CONFIRMED`, and not from a single lucky read.

- `printer-findings.md:42` records the verbatim reply, 2026-07-15 00:38:
  `X:-15.00 Y:232.50 Z:11.55 E:0.00 Count X:-1920 Y:29760 Z:4620`.
- `printer-findings.md:299-303` derives four separate calibration facts from
  repeated reads: Z is 400 steps/mm across a 51mm span; X/Y counts survive a
  power cycle while Z resets to 0; reported Z is not stable across commands.
- `printer-findings.md:307-309` (committed `3e63450`, 2026-07-19) records
  `M114` reads bracketing the 1mm, 10mm, and 3×50mm supervised jog sequences —
  **at least four more successful round trips on a second date.**

So "position is poll-only via `M114`" is **not** an untested assumption in our
notes. The polling half is well evidenced. What *is* assumption-shaped is what a
poll proves — see below.

### The path a reply takes

`CONFIRMED`, and it is not the obvious one.

`M114` is sent as `{"commandType": 1043, "cmdData": "M114", "cmdLen": 4}`
(`printer-findings.md:107-113`). The reply comes back **over MQTT**, as another
`1043` message carrying `resData`. It does **not** come back on the send
channel: `printer-findings.md:123` records the gotcha that `/ws/ctrl` answering
`{"ankerctl": 1}` is ankerctl's own ack, not the printer's, and
`scripts/printer-probe.py:78-80` carries the same warning inline. Replies also
carry an Anker-specific `+ringbuf:N,512,M` suffix to be stripped
(`printer-findings.md:129`).

There is no other channel. `local-control-research.md:190-215` proves the PPPP
JSON endpoint does not serve maker command types at all: probing
`APP_QUERY_STATUS` over PPPP returned the same 36 zero bytes as an invalid
command type 60000, so the endpoint is not parsing commands. **MQTT `1043` is the
only path.** `CONFIRMED`.

Two consumers already read these replies:

- `web/__init__.py:326-343` — `ctrl_send_mqtt` taps the MQTT service, matches the
  first reply whose `commandType` equals the request's, with a 10s timeout.
- `web/printer_actions.py:852-882` — `prepare_bed` does the same inside the
  action layer: it sends `G36` then `M400`, taps replies, filters on
  `commandType != 0x0413`, and returns only when a reply has `reply == 0` and
  `"ok"` in `resData`. **This is a working precedent for an action confirming
  itself from a G-code reply without any snapshot fact.**

### What `M114` actually reports on this firmware build

`CONFIRMED` from firmware source, and this materially constrains any contract.

All three M114 build options are disabled in
[`Configuration_adv.h`](https://github.com/eufymake/eufyMake-Marlin-M5C/blob/main/release_marlin2.0/Marlin/Configuration/V8110/V8110_DVT/Configuration_adv.h):

```
3704://#define M114_DETAIL
3705://#define M114_REALTIME
3706://#define M114_LEGACY
```

With all three off,
[`M114.cpp`](https://github.com/eufymake/eufyMake-Marlin-M5C/blob/main/release_marlin2.0/Marlin/src/gcode/host/M114.cpp)
falls straight through to a single call:

```cpp
TERN_(M114_LEGACY, planner.synchronize());
report_current_position_projected();
```

And in
[`motion.cpp`](https://github.com/eufymake/eufyMake-Marlin-M5C/blob/main/release_marlin2.0/Marlin/src/module/motion.cpp):

```cpp
void report_current_position_projected() {
  report_logical_position(current_position);
  stepper.report_a_position(planner.position);
}
```

Read carefully, this says three things:

1. **No planner sync.** `M114_LEGACY` is off, so `M114` returns immediately
   without waiting for queued moves to finish. Marlin's own comment on the
   function says this "avoid[s] planner sync that definitively interrupts the
   printing flow."
2. **`X:` `Y:` `Z:` is `current_position`** — the logical position *after the
   most recently parsed G-code*, i.e. the commanded endpoint, not where the
   toolhead is.
3. **`Count X:` is `planner.position`, not live stepper counts.** The
   `M114_REALTIME` path (`report_real_position()`, forward kinematics from actual
   steppers) is compiled out. The `Count` field the ledger has been treating as
   "raw stepper counts" is the planner's step-space endpoint.

The ledger's description at `printer-findings.md:42` — "Reports position **and
raw stepper counts**" — is therefore **imprecise for this build**. The
quantitative facts derived from it (400 steps/mm, X/Y persistence across reboot)
are unaffected; the interpretive claim "these are physical step counts" is not
supported by the source. This is a candidate correction for the ledger, at
`CONFIRMED` grade, from firmware source.

### What that means `M114` can and cannot prove

| Claim | Can `M114` establish it? | Status |
| --- | --- | --- |
| The firmware parsed and accepted the move | **Yes** — `current_position` advances only on acceptance | `CONFIRMED` |
| The move was refused (unhomed axis) | **Yes** — position unchanged, and the reply itself carries `echo:Home X` | `CONFIRMED` (`printer-findings.md:310`) |
| The move was queued into the planner | **Yes** — `planner.position` advances | `CONFIRMED` |
| The move has finished executing | **Only with `M400` first** — `M114` alone does not sync | `CONFIRMED` |
| The toolhead physically moved | **No.** Marlin is open-loop; skipped steps, a stalled axis, or a belt off its pulley are all invisible | `CONFIRMED` |

The last row is not a limitation of `M114` — it is a property of the machine.
No command on this printer can report physical displacement. The camera is
explicitly ruled out as an interlock at `printer-findings.md:583`: ~3 px/mm means
0.1mm ≈ 0.3px, "it cannot detect contact and must never be treated as a crash
interlock." It is good for gross motion only.

This distinction has already bitten this project once, in the exact opposite
direction: on 2026-07-19, X/Y jog requests were "accepted" with replies, and
`M114` correctly reported no change, and only the operator's eyes closed the
loop. A confirmation contract that had asserted "position unchanged → nothing
happened" would have been right that time. One that asserted "position changed →
it moved" would be trusting the planner's opinion.

### One caveat about `NO_WORKSPACE_OFFSETS`

`Configuration_adv.h:3701` has `#define NO_WORKSPACE_OFFSETS`, which disables
`M206`/`M428` and reverts `G92` to Marlin 1.0 behavior. Relevant to the ledger's
proposed `G92 Z0` logical-zeroing mechanism (`printer-findings.md:74`, still
`UNVERIFIED`) and to any contract that assumes logical and native coordinates can
diverge. On this build they largely cannot. `CONFIRMED` from source; the
consequence for `G92` is `UNVERIFIED` and outside this document's scope.

## What a jog confirmation contract could actually be built on

Given the evidence, here is what is genuinely available. The honest headline:
**jog is confirmable, but only up to "the firmware accepted, queued, and drained
this move" — never "the toolhead moved."** That is strictly better than
`fan_setting`, and strictly worse than the temperature actions, whose
confirmation is a real physical measurement.

### The observables that exist today

1. **`M114` position delta.** The strongest signal. Confirms acceptance, and
   with `M400` in front of it, completion of the queue. `CONFIRMED` available.
2. **The refusal echo.** `echo:Home X` / `echo:Home Y` in the `1043` `resData`
   is a *positive, specific* failure signal for the unhomed-axis case that
   defeated every X/Y jog on 2026-07-19. `CONFIRMED` observed. A contract that
   surfaced this as a named rejection reason would turn today's silent no-op into
   an accurate "this printer will not move an unhomed axis."
3. **`M400` as a completion barrier.** Already live-exercised inside
   `prepare_bed` (`web/printer_actions.py:852-882`), where `M400`'s terminal
   `ok` is the completion signal for `G36`. `CONFIRMED` as a working pattern.
4. **Operator eyes.** The only source that has ever established physical motion
   on this printer, and the one the ledger keeps concluding in favor of
   (`printer-findings.md:566-568`: "when this printer has a hard problem, the
   answer has repeatedly been its own physical interface or the runbook").

### Three shapes the contract could take

**A. Out-of-band round trip, no new facts.** Mirror `prepare_bed` exactly: inside
the compound action, read `M114`, send `G91` / `G1` / `G90`, send `M400`, read
`M114` again, and confirm on the expected delta within tolerance. Nothing is
added to `FACT_PATHS`; the snapshot stays observation-only and position never
becomes a stale-able fact. This is the smallest change, it reuses a live-proven
pattern, and the freshness problem that plagues `state` (`printer-findings.md:534-542`)
never arises because the read is synchronous with the action.

Costs: the action holds a reply tap for the duration; `M400` blocks until the
move drains, so the timeout must bound the longest permitted jog; and the
confirmation is planner-space, so the outcome string must say so honestly
(something nearer "move completed" than "printer moved").

**B. Position facts in `FACT_PATHS`, fed by a polled `M114`.** Add
`position.x/y/z` and let something poll. This is what the handoff assumed
(`handoff.md:280-286`), and it is the option with the worst failure mode:
position would inherit exactly the staleness pathology that `state` has, where
"a fan request in normal operation will fail its freshness gate unless something
polls status immediately beforehand" (`printer-findings.md:538-540`). It also
means a background poller sending G-code on a timer — and `printer-findings.md:385`
already records that fixed-rate `M105` polling was *removed* as redundant. Adding
a new fixed-rate poll of a *motion* command right after removing a temperature
one deserves a hard look. Recommend against unless a UI position readout is
independently wanted, in which case it is a separate feature from jog
confirmation.

**C. Accept `indeterminate`.** Available, and the wrong answer here. It is right
for `fan_setting` because no evidence can ever exist. For jog, evidence exists
and is one round trip away; choosing not to collect it would also reproduce the
alarm-fatigue problem the `fan_setting` decision is currently stuck on
(`handoff.md`, "The `fan_setting` decision"), for an action where it is avoidable.

**Recommendation: A**, with the refusal echo (observable 2) surfaced as a
first-class rejection reason, and with the outcome vocabulary saying "accepted
and completed" rather than implying observed physical motion. If the honest
distinction between "planner completed the move" and "the toolhead moved" needs
to live in the type system, that is the same design question the `unconfirmable`
status option in the `fan_setting` decision raises — worth deciding once for
both.

### What this does not answer, and what would

Two open questions, both closable by read-only or observe-only work:

1. ~~**Does the 1027 burst contain position?**~~ **Done, 2026-07-27 — it does
   not.** `scripts/printer-probe.py status` was run read-only and all thirteen
   non-temperature types are transcribed in the ledger. The enumeration gap
   standing since 2026-07-14 is closed and that subcommand's live path is now
   validated. What it left open: whether `1005` is fan speed.
2. **What does the official app send for jog?** Watch the local broker while the
   operator jogs from the eufyMake app. We observe; the app commands. Settles
   whether `0x400`/`0x401` are the jog opcodes and hands us their payload shape
   in one session. Requires operator presence because the app will move the
   printer, and requires it be recorded that *we* sent nothing.

Until (2) is done, **do not build issue #12 on `MOVE_STEP`/`MOVE_DIRECTION`.**
The memory note recommending it rests on opcode names and on a claim about the
firmware source that is refuted above. Building on those opcodes means guessing
a payload and sending it to a printer that has twice driven its nozzle into the
plate when we guessed at a motion opcode (`G28` and `MOVE_ZERO`,
`printer-findings.md:222-229`). The raw-G-code path is an invention, but it is an
invention whose failure mode is *refusal*, which is the safe direction.
