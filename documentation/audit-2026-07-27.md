# Audit 2026-07-27 — contradictions and unsupported claims

A sweep of every claim-bearing document in the repo plus the agent memory notes,
against the source hierarchy now defined in [`method.md`](method.md).

**Scope:** `documentation/*.md`, `handoff.md`, `CONTEXT.md`, `CLAUDE.md`,
`AGENTS.md`, `docs/adr/`, `docs/agents/`, and the twelve agent memory notes —
roughly 4,800 lines. Code comments were checked only where a document cited them.

**What this is not:** a rewrite. Findings are listed with a disposition. Fixed
ones say where; open ones are open on purpose, because deciding them needs either
the operator or Tier 1 reading that has not happened yet.

Severity is about *consequence*, not tone. **Critical** = it licensed or could
license an unsafe or wasted action. **Major** = a load-bearing claim is stated
above its evidence. **Minor** = stale or inconsistent, low blast radius.

## Critical

### A1 — The doctrine note lists our own reverse-engineering as "primary sources"

**Where:** memory `read-primary-sources-not-ask`, under "Primary sources":
`specification/mqtt.stf`, `specification/pppp.stf`, `libflagship/`.

**Why it matters.** This is the root cause of most of what follows. Those are
Tier 3 — our hypotheses, written down. Listing them beside the official firmware
repo makes "the spec says so" look like a citation. On 2026-07-27 that licensed
the argument *"`0x3ed` is solid because `mqtt.stf` declares it unhedged"*, used
to justify sending an unexercised opcode to the printer. The rule intended to
prevent guessing was itself authorising it.

**Disposition:** FIXED — memory note corrected to tier its sources and point at
`method.md`.

### A2 — "The Linux upper computer has never been published"

**Where:** `jog-confirmation-research.md:128`, repeated verbally as settled.

**Reality:** `eufymake/eufyMake-linux-sdk` is public under GPL-3.0. The claim was
reached by searching only the Marlin repo and generalising from its absence
there. Two vendor trees *inside* the Marlin repo were also missed:
`src/gcode/anker_gcode/` (six files) and `src/feature/anker/` (fourteen modules,
including `anker_homing`, `anker_z_sensorless`, `anker_z_offset`, `anker_pause`,
`handshake`).

**Why it matters.** It closed off the highest-value line of investigation and
made "capture the official app" look like the only route to opcode payloads —
which would have meant scheduling printer time to learn something that may be
readable for free.

**Disposition:** FIXED — corrected in place, commit `81baa6e`.

### A3 — "This printer publishes no fan-state fact"

**Where:** `handoff.md` ("The `fan_setting` decision"),
`printer-test-validation.md:279`, `printer-findings.md:354`, and until today
`static/ankersrv.js` — shown to the operator on every fan command.

**Reality:** unsupported as written. It rests on the 1027 burst exposing no fan
field, but the burst contains type **1005**, which our own table names
`ZZ_MQTT_CMD_FAN_SPEED` (`0x3ed`). The original conclusion appears to be an
inference over types nobody had decoded.

What is now established (Tier 0, attended, cold printer, 2026-07-27): `1005`
does not move when the fan is driven by raw `M106`/`M107`, while the operator
hears the fan run. What that does **not** establish is that the printer never
reports fan state.

Tier 1 explains the mechanism: `Temperature::report_fan_speed()` exists and is
called under `TERN_(REPORT_FAN_CHANGE, …)`, and `V8110_DVT/Configuration_adv.h`
has `//#define REPORT_FAN_CHANGE   // Report the new fan speed when changed by
M106 (and others)`. The MCU is *capable* of reporting fan changes and this build
does not. So nothing downstream — including the communication module — learns
that our `M106` changed anything.

**Disposition:** PARTLY FIXED. UI copy and `printer-findings.md` corrected;
`handoff.md` records the decision. **`printer-test-validation.md:279` still
carries the original phrasing** — left for the same pass that re-grades the fan
action, so the correction lands once rather than twice.

## Major

### B1 — Ledger contradicts itself about what `M114` reports

**Where:** `printer-findings.md:42` was corrected on 2026-07-27 to "planner
counts — **not** live stepper reality". Lines **289** and **299** still say "raw
stepper counts", one of them inside a `REFUTED` row.

**Reality:** Tier 1 — `M114_DETAIL`, `M114_REALTIME`, and `M114_LEGACY` are all
commented out for V8110_DVT, so `M114` falls through to
`report_current_position_projected()`: `Count X:` is `planner.position`.

**Why it matters:** this is load-bearing for issue #12. A jog contract built on
"stepper counts" would claim to prove physical motion; the planner's opinion
proves only that a move was accepted and queued.

**Disposition:** FIXED — both rows corrected below.

### B2 — Probe-arming gating: retracted in the ledger, asserted in memory

**Where:** `printer-findings.md:288` lists *"The probe is gated by Anker's comm
module"* under **Retracted claims** — "Plausible but never evidenced… `UNVERIFIED`
at best". Memory `m5c-homing-dead-ends` states the same idea as the settled
synthesis: *"the state that arms the nozzle probe is orchestrated by the
communication module… Raw G-code and MQTT opcodes reach the MCU but cannot arm
it."*

**Why it matters:** it is the standing reason homing is considered unreachable,
and homing is the oldest open problem with physical consequences. One artifact
calls it retracted, the other treats it as the working model.

**Disposition:** OPEN, but **the evidence now runs against the memory note.**
`anker_homing.cpp` was read on 2026-07-28. The Z-homing gate flag,
`anker_z_homing_options` ("actions that need to be performed only when zeroing
Z"), is set and cleared **inside `G28.cpp`** — `:505`, `:595`, `:770` — not by
anything the communication module owns. The custom Z path
(`anker_home_z_safely()` plus `ANKER_Z_HOMING_SCRIPT`, live via `WS1_HOMING_5X`)
is firmware-internal too.

That does not yet prove standalone `G28` *should* work, and it does not explain
why the in-print one does. But "arming lives in the comm module" now has firmware
evidence against it, and the memory note should not be treated as the working
model. Next read: what `anker_home_z_safely()` and `ANKER_Z_HOMING_SCRIPT`
actually do, and whether `ANKER_OVERPRESSURE_REPORT 0` explains the plate
strikes.

### B3 — `USE_Z_SENSORLESS` left `UNVERIFIED` when Tier 1 could settle it

**Where:** `printer-findings.md:262` — the `ANKER_PROBE_TIMEOUT` /
`ANTHER_Z_DROP_DISTANCE` block "sits inside `#if ENABLED(USE_Z_SENSORLESS)` and
`USE_Z_SENSORLESS` is not defined in either config file — may be dead code",
graded `UNVERIFIED` from a grep of two headers.

**Why it matters:** those constants describe probe descent distances. Whether
that block is live or dead bears directly on B2.

**Disposition:** **RESOLVED 2026-07-28 — and the ledger claim was wrong.**
`USE_Z_SENSORLESS` **is** defined: `#define USE_Z_SENSORLESS 1` in
`release_marlin2.0/Marlin/src/inc/ANKER_Config.h:69`. The grep behind the ledger
row covered `Configuration.h` and `Configuration_adv.h` — **there is a third
config file, and nobody knew.** The block is live code, and so is the Z-homing
retry-then-`kill` path in `anker_homing.cpp:224-234`.

This also widens the finding: the ledger's entire "Firmware facts" section was
built from two of three config files, so any row in it may have the same defect.
Recorded in the ledger's new `ANKER_Config.h` entry.

### B4 — Probe script's live paths still marked untrusted

**Where:** `printer-findings.md:95` — `pos`/`endstops`/`status`/`watch` are
"`UNVERIFIED` — printer went silent before they could be exercised… **Test before
trusting.**"

**Reality:** `status` was run three times and `gcode` twice on 2026-07-27, all
successful, and `status` produced the full 1027 enumeration.

**Disposition:** FIXED — re-graded below. `endstops` and `watch` remain
unexercised and stay `UNVERIFIED`.

## Code layer

Second pass, over comments and docstrings in `web/`, `static/`, `libflagship/`,
`scripts/`, and `tests/`.

**General standard is high**, and worth saying plainly: most comments explain
*why* rather than *what*, and several cite Tier 1 properly — `web/util.py:17-18`
derives its temperature limits from V8110 `Configuration.h` by name. The
`printer_actions.py` rationale comments around supersession, Protective
availability, and Compound-action ordering are accurate against the ledger.

One finding, and it is the most serious in this audit.

### D1 — `print_start` sends `G36` with no gate, and the documented mitigation does not work *(Critical)*

**The command.** `printer-findings.md` lists `G36` under **"Known-dangerous — do
not send"**: *"ACKs, no motion, **wedges the command queue**, needs a power
cycle."* `CONFIRMED` twice. `scripts/printer-probe.py:47` refuses to send it
outright: *"G36 wedges the command queue (needs a power cycle)"*.

**The legacy path respects that.** `web/util.py:232` runs the pre-print routine
only `if app.config.get("preprint_g36")`, bound to `ANKERCTL_PREPRINT_G36`, which
is pinned false precisely because `G36` failed on 2026-07-09.

**The named `print_start` action does not.** `printer_actions.py:512` calls
`self._protocol.prepare_bed(...)` whenever `artifact.bed_celsius is not None`,
and `prepare_bed` sends `G36` then `M400`. **`preprint_g36` is never referenced
in `printer_actions.py`.** The Compound action dropped the gate the path it
replaces still has.

**And the recorded mitigation is ineffective.** `handoff.md:304` tells the
operator that a supervised run should *"validate the unprepared path first with
`ANKERCTL_PREPRINT_G36` false"*. That variable does not reach this code path.
Setting it false changes nothing about what `print_start` sends.

**Why it has not bitten yet.** `print_start` is gated behind validation mode or
the `m5c-print-start-v1` contract, both currently off, so it cannot fire today.
The call also has a timeout — but a timeout in our process does not unwedge a
printer whose queue is stuck; the ledger says that needs a physical power cycle.

**Where it would bite.** Issue #18 — the supervised validation of upload and
print start. That run enables the action, believing `ANKERCTL_PREPRINT_G36=false`
holds `G36` back. It does not.

**A contradiction in the comment, too.** `prepare_bed`'s docstring reads *"Run
the firmware's own bed-preparation routine to completion… `M400` queues behind it
and supplies the terminal `ok` only once probing has finished."* That describes
`G36` working. Every other source in the repo says it ACKs and does nothing. One
of the two is wrong and it is not clear which — the docstring may describe an
intended design that was never observed, or `G36` may behave differently
out-of-band than inside uploaded G-code. **Nothing in the repo establishes that
it works.**

**Re-scoped 2026-07-28 — the severity was overstated and the real defect is
different.**

Two corrections to what is written above:

1. **"Wedges the queue, needs a power cycle" is contested, not established.** It
   comes from one early experiment (`local-macos-service.md:744-750`). The two
   supervised sessions on 2026-07-09 did **not** reproduce it — the printer
   reported `Idle / Ready to Print` and the emergency cooldown worked, heater
   targets verified at 0 (`printer-test-validation.md:106-109`). The ledger
   recorded only the worse outcome, graded `CONFIRMED`, and this finding
   inherited it. `method.md` §4 says the later observation does not automatically
   win — but neither does the scarier one, and no reconciliation was done.

2. **`G36` is simply the wrong command.** The OrcaSlicer Anker M5C machine
   profile — the configuration behind every successful print — has this start
   G-code:

   ```
   M4899 T3                    ; Anker custom: v3 jerk + S-curve
   M104 S150                   ; standby nozzle, prevent ooze
   M190 S{first_layer_bed_temperature}   ; set AND WAIT
   M109 S{first_layer_temperature}       ; set AND WAIT
   G28 ;Home
   ```

   `printer_actions.py:499-512` matches the first three steps and then
   substitutes `G36` for **`G28`**. The working flow never sends `G36`. (`M4899`
   is a real Anker opcode — `anker_gcode/M4200_M4900.cpp` — that we never send at
   all.)

**So the actual defect is functional, not a safety landmine.** `prepare_bed`
waits for a completion `ok` that this firmware has never once returned, so
`print_start` will reliably time out its preparation stage on any print carrying
a bed temperature. Issue #18 would fail on it.

What stands unchanged: **`ANKERCTL_PREPRINT_G36` does not gate this path**, so the
mitigation recorded in `handoff.md` was ineffective.

**Disposition:** OPEN — the design choice is now clearer. Options are to gate
`prepare_bed`, drop the preparation step, or align it with the profile's actual
sequence. **Do not run #18 until this is settled.**

## Issue tracker

Same sweep, applied to the fifteen issues. Nothing here has been changed on
GitHub — these are proposals, because editing the tracker is a visible action.

### T1 — #12 is labelled `ready-for-agent` and is not ready *(Critical)*

`triage-labels.md` defines that label as "fully specified, ready for an AFK
agent". #12's only stated blocker is **#8, which is closed**, so the tracker
reads as go. It is not: `FACT_PATHS` has no position fact, and
`jog-confirmation-research.md` concludes the confirmation contract has to be
designed before implementation begins. `handoff.md` says the same — "unblocked
but not ready to implement" — but that lives in a file no agent picking up the
ticket will read.

**Consequence:** an AFK agent starts building a motion action, on the axis that
has twice driven the nozzle into the plate, with nothing to confirm against.

**Proposed:** relabel `needs-triage` (or add a blocking design ticket) and record
the real blocker in the issue body.

### T2 — #12's eligibility criterion bakes in a known defect *(Major)*

> "Eligibility requires fresh state proving that manual motion is allowed and
> that a print is not active."

The M5C **never publishes `state`**; it exists only as a reply to
`APP_QUERY_STATUS` and is stale 15 seconds later. This exact requirement is what
produced the `fresh_printer_state_required` fan rejections on 2026-07-23 and
2026-07-26. Writing it into jog eligibility reproduces a defect we have already
paid for twice, on a more dangerous action.

### T3 — #12 has no criterion for the one confirmed jog behaviour *(Major)*

X/Y jog is `CONFIRMED` not to move: every reply carried `echo:Home X`/`echo:Home
Y`, Marlin's unhomed-axis refusal, across 1mm, 10mm, and 3×50mm supervised
sequences. No acceptance criterion mentions it. The research recommends
surfacing it as a named rejection reason, which would turn today's silent no-op
into an accurate message — but it is not in the ticket.

### T4 — #6 user story 7 promises confirmation the machine cannot give *(Major)*

> "As an operator, I want confirmed actions to be backed by an **observed printer
> outcome**, so that confirmation reflects **physical behavior** rather than
> transport acknowledgement."

This is the parent spec's central promise, and it is not uniformly achievable:

| Action class | Can confirmation reflect physical behaviour? |
| --- | --- |
| Thermal | **Yes** — thermistor readings are real measurements |
| Jog / motion | **No** — `M114` reports planner space; open-loop steppers make skipped steps invisible |
| Live Z (`M290`) | **No** — babystep is invisible to `M114` by design |
| Fan | **Unknown** — the 1005 question (A3) |

The spec needs a vocabulary that distinguishes *"the printer measured this"* from
*"the firmware accepted and drained this"*. Note #13 already handles the tension
correctly — "effects that cannot be reliably observed… become indeterminate and
are never falsely reported as confirmed" — while #12 does not. Worth propagating
#13's wording upward.

### T5 — #15's pinned comment publishes the A3 claim *(Major)*

The 2026-07-26 comment states: *"Fan speed has no telemetry, so a fan request can
only ever reach `indeterminate/confirmation_unavailable`… This is a property of
the M5C, not a fixture that can be improved."* That is A3, on the public tracker,
as the justification for a disposition. Needs a correction comment recording the
2026-07-27 test and the open 1005 question.

The rest of that comment stands — the three thermal contracts are still the right
disposition.

### T6 — #17 contains criteria that cannot pass today *(Minor)*

"Jog moves only the requested axis by the bounded amount" cannot pass for X/Y
while unhomed-axis refusal stands, and "live Z adjustment produces the expected
bounded effect" has no instrument, since `M290` is invisible to `M114`. Neither
is wrong as an aspiration; both would fail a validation run for reasons that have
nothing to do with the code under test.

### T7 — `ready-for-agent` on tickets with open blockers *(Minor)*

#13 (blocked by #12) and #19 (blocked by #9, #15, #16, #17, #18) both carry
`ready-for-agent`. Under the label's own definition they are not actionable. Low
harm — the blocker lists are visible — but it makes the label meaningless as a
work queue.

## The pattern worth naming

`printer-test-validation.md:181` shows the 2026-07-10 Stop investigation was
resolved *"against the published firmware source and a live MQTT capture"*, and
`:220` cites `anker_pause.cpp:240` by line. That is Tier 1 work, and it produced
the most durable result in the project — the `PRINT_CONTROL` payload that still
holds.

The later drift to black-box probing is the regression. Today's fan test is the
clearest case: an attended live test was run to answer a question a one-line grep
of published source answers definitively, and the analysis of the result cited
our own spec file as the authority.

**The corrective is not more caution. It is reading the sources that already
exist before spending printer time.**
